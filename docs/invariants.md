# Implementation invariants

This file owns textcast-chat-axi's architecture internals, security rationale, and easy-to-reintroduce failure modes.
[AGENTS.md](../AGENTS.md) keeps only the every-session rules and points here.
[README.md](../README.md) owns the user-facing contract. Runtime guidance strings in `src/cli.js` own what agents are told while using textcast.

When a change touches an invariant below, update this file. When it touches a user-facing contract, update the README instead.

## Architecture

Textcast Chat is a CLI + local HTTP server that opens agent-generated HTML artifacts in a browser, lets the user annotate elements and selected text ranges, and ships that feedback back to the agent over a long-polling API.

### Process model

Tailscale detection (`src/tailscale.js`) resolves each command candidate to an executable regular file before calling `execFile`: absolute paths are checked directly and bare names are resolved through `PATH`. Unresolved candidates are skipped without a launch attempt, because even an attempted launch of a missing binary can trigger managed-device software restrictions. Resolution and probe errors remain non-fatal, and all candidates share one probe timeout budget. `test/tailscale.test.js` covers skipping missing, directory, and non-executable candidates while retaining probes of installed executables.

The CLI (`bin/textcast-chat-axi.js` -> `src/cli.js`) spawns `textcast-chat-axi server` as a **detached** background process (`src/cli.js:startServer`) and waits for `/health`, which returns `{ ok, app, version }`.
Later CLI invocations reuse the running server when its health version is equal to or newer than the current CLI version, and replace it when the version is older, missing before the handshake, or unparseable, or when the local-build force applies. Releases up to and including 0.1.86 still replace a server of a different version. Stale servers are asked to `POST /shutdown`, and a pre-handshake server may be SIGTERM'd only through the PID `lsof` finds listening at its exact address and port whose command is Textcast Chat (`killTextcastListener`); other processes can share the port at other addresses, so nothing is ever signalled by port alone, and an unidentifiable listener is reported instead.
Host, port, listener, and link-host resolution lives in `src/paths.js`; the default path detects Tailscale and gives `serve()` separate concrete loopback and Tailscale listeners, and an explicit `TEXTCAST_CHAT_AXI_HOST` disables that automatic path but still adds loopback beside the pinned address. Loopback is always requested because it is the one address every CLI probes regardless of its own `TEXTCAST_CHAT_AXI_HOST`: agents on one machine run with different settings, and a server pinned to the tailnet address alone was invisible to a client with no host, which then spawned a second daemon on the same port and the same `state.json`. Wildcard requests are reduced to loopback before listening, and aliases are DNS-resolved and rejected if any result is an all-interfaces address. A name that does not resolve right now is kept as the name (`keepUnresolved`) on both sides - the server binds and retries it like any failed address and reports it in `network_warning`, and the CLI still requires it - so a DNS failure never silently drops an explicit `TEXTCAST_CHAT_AXI_HOST`. `listenOnce` resolves a name through the same lookup and all-interfaces refusal as startup, and `requested_hosts` reports configured names beside the addresses they resolved to, so a name whose DNS recovers is compared by address and never looks missing to a CLI that resolves it. Loopback binds FIRST and is the port's ownership lock: if it is in use by a Textcast Chat server (probed over `/health`, bounded), startup throws before taking any other address, so two servers started concurrently cannot split one port between them. Every concrete address gets the same bounded bind retry, and the "did anything bind yet" check runs AFTER those retries and after the loopback floor below - ordering it first made both unreachable whenever the first (or only) host failed. When nothing binds and loopback was not among the requested hosts (explicit `hosts` only), `serve()` binds loopback as a floor. At least one listener must be an address the CLI control channel probes (the primary requested host or loopback), otherwise every listener already bound is closed and startup throws. A requested address that still fails is NOT given up on and never marks the server stale: it stays in `pendingBinds`, is retried in the background for the life of the process (`BIND_RECOVERY_DELAYS_MS`, last delay repeating) and immediately on `/health?reconcile_network=1`, and `applyNetworkState` recomputes the link host, Host allowlist, and phone readiness whenever a listener comes up. Restarting could not free a port another process holds and would drop every live review connection. Every surface that reports network health derives its text from `pendingBinds` (`currentNetworkWarning`), so the warning appears and clears with the bind state and is always logged, not only under `--verbose`. Every mutable the request handlers touch (`idleTimer`, `attachmentSweepTimer`, `bindRecoveryTimer`) is declared before the first listener binds: a reconnecting chrome can attach a live-event socket while later addresses are still retrying, and declaring them after the bind loop was a TDZ `ReferenceError` that crashed restarted servers. CLI discovery (`findRunningServer` in `src/cli.js`) probes the configured host, loopback, and every local interface address in parallel, each bounded, and a response whose `app` is `textcast-chat-axi` wins over a foreign `/health`. Both health probes (`fetchHealth` in the CLI, `probeTextcastHealth` in the server) use `node:http` with the socket destroyed on every exit path, never `fetch`: an aborted fetch leaves its TCP connect running, and a Tailscale IPv6 address that drops connections to itself kept every CLI invocation alive ~10s after printing; a connection nobody reads likewise holds the other side's `close()` open. `/health` reports `state_id` (hash of the state file path), `state_dir`, bound `hosts`, and `requested_hosts`. Installation identity is `isOwnedServer`: a matching `state_id`, or - for a 0.1.77-or-older server that reports none - an answer at the CLI's configured host or loopback, where replacing it is the upgrade path; one reached only through the interface sweep without a `state_id` is never adopted or stopped, and another installation's server at a control address is a `SERVER_ERROR` naming its state directory, never used, replaced, or stopped. The CLI adopts the first owned server, retires any other owned server on the port over its own `/shutdown` (never by process name or port-wide signal), and replaces the kept server first when it does not request every address a retired duplicate served (`hostsToServe`), so existing review links survive. It also replaces a server whose `requested_hosts` lack the CLI's explicit host, rechecked once in the startup wait loop when another daemon wins the port, so agents with different hosts converge on one daemon instead of trading it; a server still missing that host after the one retry (including after a network restart) is a `SERVER_ERROR` naming the address, never a successful open. Every replacement - missing host, upgrade, or changed network - passes everything the replaced servers requested to the new one (`inheritedListenHosts` -> `--also-listen`), so one agent's restart never drops another agent's address and its review links; only an IP that is no longer on a local interface (`localInterfaceAddresses`) is dropped, so a vanished Tailscale address is not retried forever while a still-live one survives a MagicDNS change even when the replacing agent's explicit host disables Tailscale detection. A Tailscale identity change (address, MagicDNS, up/down) still reports `network_stale` and is replaced by `ensureServer`, at most once per invocation including the replacement performed before the startup wait loop; a version-driven replacement does not consume that network guard. A version-driven replacement happens only when the running server is OLDER than the CLI (`isServerOlderThanCli`, numeric on major.minor.patch): a newer server is adopted, because replacing it in either direction made two installed versions restart each other's server and interrupt every live poll. Releases up to and including 0.1.86 still replace a server of a different version, so this stops only when both installed versions contain this fix. The same test gates the SIGTERM fallback (`shouldKillProcessOnPort`) and the `upgrade` reason. A missing or unparseable version still counts as older, and the local-build force still replaces a server of any version.
Two global middlewares run before every route, in this order: a Host-header allowlist, then a mutating-route Origin/Referer guard. The Host allowlist (`buildAllowedHostnames`/`isAllowedRequestHost`) rejects any request whose `Host` is missing or not one this server answers to - the DNS-rebinding defense, since `isSameOriginRequest` alone does not stop rebinding (a rebound page sends its hostile domain in _both_ `Origin` and `Host`, so they still match). The allowlist is loopback names + every concrete listener + the active link host + explicit `TEXTCAST_CHAT_AXI_ALLOWED_HOSTS` extras (`src/paths.js:extraAllowedHosts`), minus wildcard binds; the Tailscale address and MagicDNS name enter it only while the Tailscale listener is usable. A lone `*` (`allowsAllHosts`) disables the guard for operators fronting it with their own auth. When a reverse proxy sits in front, `X-Forwarded-Host`'s outermost value is validated as a complete authority against the same allowlist (an AND check, so a spoofed or malformed forwarded host only narrows access, never bypasses `Host`); the `*` opt-out skips hostname membership but still rejects malformed authorities. README's Allowed hosts bullet owns the user-facing contract. So a specific-interface bind stays rebinding-protected while its own hostname works, rather than the guard switching off outside loopback. The origin guard then 403s non-GET/HEAD/OPTIONS requests whose Origin (else Referer) is present and does not match this server's origin, using the same construction as `isSameOriginRequest` (including forwarded host/proto). Header-less CLI control-channel requests have no Origin and must keep working; the Host allowlist remains their gate. Per-route `isSameOriginRequest` checks stay in place and still reject header-less callers.
README's Network binding bullet owns the user-facing env vars and the non-loopback security warning.
Live-event WebSockets carry an application-level ping/pong (`liveEventHeartbeatMs`) and an unanswered ping terminates the socket, because a slept laptop or a dropped tailnet path leaves a half-open connection that never emits `close` - which otherwise keeps a departed reviewer counted, suppressing idle shutdown and reporting presence wrongly. Every `shutdown()` records a log-only `cause` (never widened into the user-facing `reason`, which would let an internal cause render as a banner line that claims something untrue), and default log lines are UTC-timestamped by `formatServerLogLine` because `server.log` is append-only across restarts. Detached server stdout/stderr are timestamped inside the server process at real line starts so crash diagnostics in `server.log` stay dated after the parent CLI has already exited; an injected `log` still formats its own lines. The detached spawn uses `bin/textcast-chat-axi-server.js` (published as `dist/server.mjs`), which installs that writer before dynamically importing the CLI, so a module-load failure is dated too. Each HTTP listener keeps its `error` handler after `listening`, so a post-listen error is logged instead of becoming a fatal unhandled `EventEmitter` error. The detached entrypoint also logs `uncaughtException` through timestamped stderr and exits 1 explicitly; installing that listener without an explicit exit would suppress Node's default termination and leave a potentially corrupted server alive. Ordinary user-facing commands still start through `bin/textcast-chat-axi.js` / `dist/cli.mjs`. Server self-shutdown keys off tracked live connections (browser WebSockets and agent polls), not session status, so the next `textcast-chat-axi <file>` re-spawns a fresh server and adopts the session from `state.json` when it is still resumable; README's Server cleanup bullet owns the user-facing idle-timeout rules. The retained legacy SSE route is only a one-response migration handoff, not a tracked persistent connection.
State lives at `~/.textcast-chat-axi/state.json` (`TEXTCAST_CHAT_AXI_STATE_DIR`), shared across all projects and keyed by a sha256 prefix of the canonicalized file path - the canonical HTML path _is_ the identity, so the CLI never needs opaque session IDs (`src/session-store.js:sessionKey`).
That makes the session key **derived, not secret**: anyone who learns the artifact path (or sees a session URL) knows it, so no route may treat key possession as authorization.

### Request flow

1. `textcast-chat-axi <file.html>` (`openCommand`) -> POST `/api/sessions` -> `SessionStore.upsertSession` -> the CLI opens the returned session URL in the browser.
   Sessions record who ended them: `ended_by: "user"` for browser-initiated ends (including the composer's send-and-end, which posts final prompts and the `endSession` flag to `/api/:key/prompts` atomically) and `ended_by: "agent"` for `textcast-chat-axi end <file>`.
   Idle self-shutdown never calls `endSession` - it only stops the server process, leaving session status untouched in `state.json`, so there is no third `ended_by` case to track.
   `/api/sessions` refuses a path that is not a regular `.html` / `.htm` file after `realpath` (`src/artifact-path.js:resolveAllowedArtifactFile`), matching the CLI, so a caller cannot register `/etc/passwd` (or an HTML symlink to it) and adopt that directory as a serving tree.
   `/api/sessions` refuses to revive a user-ended session unless the request body sets `reopen: true` (the CLI's `--reopen`), returning `{ status: "user-ended" }` without upserting; agent-initiated ends keep reviving on a plain open.
2. `GET /session/:key` serves a chrome page (`createChromeHtml`) whose sandboxed iframe points at `/artifact/:key/index.html`; the chrome client bootstraps from the `textcast-session` JSON script in the page.
   `extractArtifactHead` (`src/server.js`) adopts the artifact's own `<title>` and `<link rel="icon">` for the chrome tab, but only `data:`, `http(s):`, and protocol-relative icon hrefs - artifact-relative hrefs would not resolve against the chrome page - with fallback to the Textcast Chat defaults.
3. The artifact route runs `injectTextcastSdk` (`src/html-transform.js`) to append one `<script src="/sdk.js?key=...">` at the end of `<body>`. Nothing else is injected - artifacts stay byte-identical apart from that tag so they remain portable when opened directly without the server.
4. Sibling assets resolve under `/artifact/:key/<path>`, sandboxed to that session's **artifact tree** - the directory of the canonical HTML file - both lexically and by **real-path/symlink resolution**. `resolveArtifactAsset` rejects `..` escapes and a path whose symlink-followed real path leaves the tree, so a symlink placed beside the artifact can't make the route serve an outside file; a nonexistent path (`ENOENT`/`ENOTDIR`) falls back to the lexical check for the caller's 404, and every other realpath failure fails closed. It returns the **resolved** path, so `sendFile` re-opening it cannot be redirected by a link swapped in after the check. `sendFile` still uses `dotfiles: "allow"` so a tree that _lives under_ a dot-directory (`.textcast/artifact.html`) is not 403ed by the absolute path. A stored session whose file is not HTML is refused on `/artifact` and `/session/:key` before those routes read `session.file`.
5. Nothing covers or hides the artifact while it loads. Once the document has parsed, the injected SDK posts its theme report (`textcast:theme`) and then `textcast:ready`; nothing about either goes to the server. If a ready report loses an artifact-load-token race, the chrome asks the current document for a fresh one (`textcast:requestReady`) instead of consuming the cycle.
   The narrow **fatal** path is separate and still immediate: `/api/:key/artifact-failures` records only `artifact-unavailable` (the chrome's probe of the artifact route failed) or `artifact-asset-unavailable` (the SDK saw a same-origin subresource `error`), marks the session `feedback`, and `takeFeedback` returns them as `artifact_failures`.
6. User actions in the iframe `postMessage` to the chrome. Queued prompts live in tab `sessionStorage`; unsent prompts sharing the SDK-internal `_textcastQueueKey` replace each other, and that field is stripped before POSTing collected prompts to `/api/:key/prompts`.
   The chrome assigns each queued prompt a unique `prompt_id` at queue time (never trusting an iframe-supplied value), carries it through `queuePrompts` onto the persisted transcript entry, and removes a queued note solely when that transcript acknowledges the same identity - never by displayed content or only by a successful POST response - so a reload after a lost response recognizes an already-accepted note instead of re-sending it. `queuePrompts` filters acknowledged identities before attachment resolution and layout-warning planning, and reports whether it accepted fresh feedback so an idempotent retry neither conflicts with newer warning state nor wakes an unrelated poll. Visible `session.chat` is bounded to `MAX_CHAT_STORED_BYTES` (5,242,880) of stored JSON on every shared state load and transcript append; legacy overflow is persisted before the session is served. Evicted user entries leave their `prompt_id` on `session.chat_ack_ids`, and both the store's ack filter and the chrome's settlement (`initialChatAckIds` / live `ack_ids`) consult that compact list so eviction cannot reopen duplicate send. `chat_revision` lets the chrome accept an authoritative bounded replacement even when no retained entry overlaps its current view, while rejecting stale syncs.
   Editing a queued note happens only in the chrome: the edit rewrites `prompt` on the same queued object, so its `prompt_id`, anchor, and send bookkeeping (which tracks notes by object identity) are unchanged, and a note that is already Sending cannot be opened. The iframe learns only the selectors of element-anchored queued notes (`textcast:queuedAnchors`), never their text, and asks the chrome to open one with `textcast:editQueuedAnchor`. The artifact is agent-authored, so a design where the SDK held or rewrote note text would let any artifact script read or silently rewrite the reviewer's instructions; the forgeable message can only open one of the user's own notes for editing.
   The conversation transcript is server-owned display state. Every accepted prompt with text or images enters `session.chat` through `chatEntryForPrompt` (`src/chat-messages.js`) as a bounded `{ role: "user", kind, text, anchor, attachments, at, prompt_id }` entry - not only composer messages - and `/api/:key/prompts` answers with the serialized transcript and emits `chat-sync` at accept time, so the sending chrome settles its queued bubbles in place and every other tab shows the sent notes before any poll takes the batch. Rendering is computed server-side by `serializeChat`/`renderChatMarkdown` in that module because `chrome-client.js` is served as a raw file and cannot import modules (the same reason layout-warning display strings and share passwords are): agent entries ship with their rendered `html` and are the only entries the chrome ever sets as html; user entries ship as text with their anchor and are always escaped. The queued log (`#queuedLog`, the last child of `.panel-scroll`) renders the tab's unsent prompts as the same user bubble in its dashed, removable state, and `promptAnchor` in the chrome deliberately duplicates the server's anchor rule for prompts that have not reached the server yet; `test/chrome-client-queue.test.js` pins the two against the same fixtures so a bubble never changes its anchor when it settles. A note's Sending state is derived from the existing send bookkeeping (`snapshotRequests`, `pendingSubmissions`, the active submission, the terminal reservation), never tracked separately, so no failure path can strand a note with its remove control disabled.
   `/api/:key/prompts` is **same-origin guarded** like the attachment upload and delete routes: whatever lands there reaches the agent as the reviewer's own instructions, and the key alone must never buy that. Only this server's own chrome may queue prompts, so any test or tool that posts there has to send a matching `Origin`; behind a reverse proxy, the expected origin is built from the outermost `X-Forwarded-Host`'s validated hostname and port plus the outermost `X-Forwarded-Proto`, only after the forwarded authority passes the same allowlist boundary as `Host` (or strict authority validation under the `*` opt-out).
   The route rejects every new batch for an already-ended session, including a redundant send-and-end batch, because no later poll will deliver it. `SessionStore.queuePrompts` exempts only its internal `restore` replay of a batch that was accepted before a poll disconnected.
   The chrome page (`/session/:key`) also answers `X-Frame-Options: DENY` and `frame-ancestors 'none'`, denying an attacker page both a window handle to the chrome and a clickjacking surface over Send. The header is scoped to that route on purpose - `/artifact/*` is framed by the chrome.
   Text selection prompts use `tag: "text"` with a `target` of `type: "text-range"` (selected text, `commonAncestorSelector`, start/end boundary anchors).
   Composer and annotation-card keyboard conventions, button layout, and the conversation panel are user-facing behavior owned by README's Feedback controls and Keyboard shortcuts bullets.
7. `textcast-chat-axi poll <file.html>` (`pollCommand`) hits `GET /api/poll`, or `POST /api/poll` when it atomically publishes an `--agent-reply` before waiting.
   Poll ownership is exclusive per session and lives only in the server's `activePolls` map. A second poll receives typed `LISTENER_ACTIVE` with the holder label and age; `--takeover` installs its holder before releasing the old poll with typed `LISTENER_REPLACED`, so cleanup cannot erase the successor. The in-process map also supplies the listener labels exposed by `/health` for session listings. Claims serialize through `pollOwnershipLock`, including the reply write, so a rejected poll cannot publish or duplicate its reply. Poll control GETs and POSTs reject a present foreign Origin or Referer while preserving header-less CLI access.
   Queued prompts or fatal artifact failures - including prompts queued before an ended session - are returned immediately and mark the session as observed by an agent; otherwise the poll marks the session actively listening and long-polls on an `EventEmitter` until a `feedback` or `ended` event fires.
   A waiting no-timeout response carries `Textcast-Poll-State: listening`; immediate feedback does not. The CLI uses that response signal for the opt-in Herdr chime, so it never announces a review-ready wait when feedback was already queued, and notification failure must never affect the poll.
   A `status: "ended"` response carries `ended_by`; the final `status: "feedback"` batch delivered right before a session ends carries the same signal via `session_ended: true` plus `ended_by`, so that last `next_step` also skips the reopen instruction.
   Default no-timeout polls stream whitespace heartbeat bytes before the final JSON response and always write the one-shot wait banner to stderr - it is the "not hung" signal an agent needs while stdout stays empty - but write the recurring per-minute wait ticks only when stderr is an interactive terminal (`shouldNarratePollWaitTicks`), so agent harnesses with piped, non-TTY stdio get no unbounded tick noise in their merged capture; stdout is always reserved for the final JSON/TOON response, and `--timeout-ms` is a non-streaming test/debug escape hatch.
   Losing the last review WebSocket while a poll is active starts a per-session reconnect grace timer; a reconnect cancels it, while expiry releases the poll with non-terminal `browser_disconnected` and leaves the stored session open. Poll cleanup must cancel that timer so a timeout, feedback, or explicit end cannot leave a stale disconnect event for a later poll. A disabled grace (`resolveBrowserDisconnectGraceMs` returns `null`) must schedule no timer at all, never a `null`/`0` delay, which `setTimeout` would fire almost at once.
   Key order in `createPollOutput`'s feedback object is a contract, not incidental: `prompts`, `artifact_failures`, then `next_step`, so an agent that truncates or filters the response still reaches the user's own words and the instruction that continues the review loop (`test/cli-output.test.js` guards the emitted order). No DOM snapshot is collected or emitted: Textcast notes locate their target by segment selector. Never bury `next_step` behind a bulky field: it is the only field carrying the reply-and-poll-again directive, the attachment paths, and the session-ended "stop polling" rule. Poll delivery consumes the response - the feedback is gone from the store once returned - which is why the guidance strings say feedback remains queued only _until delivery_ rather than that it is never lost.
   If SIGINT or SIGTERM interrupts a no-timeout poll, the CLI writes re-run guidance to stderr and exits with the conventional signal code; queued feedback persists, so re-running the same poll is safe.
   That durability has to survive the take itself: `takeFeedback` clears the batch before any response is written, so a poll whose client disconnected - during the immediate take OR during the event-driven long-poll `respond()` - puts the prompts, `dom_snapshot`, and `artifact_failures` back through `queuePrompts`'s `restore` mode and leaves delivery unmarked, because nothing was delivered. `restore` replays an already-accepted batch verbatim - it re-plans no layout warnings and re-appends no chat messages - while still re-deriving attachments through the same resolver.
   Everything else about restore exists because the take window is concurrent, and each rule is load-bearing. Restored prompts are PREPENDED, so a `/prompts` that landed in the window keeps its later position and the user's chronological order survives. Newer `artifact_failures` WIN - the restore only fills what the window did not already replace, and the failure merge goes through the same `mergeArtifactFailures` dedupe and `MAX_ARTIFACT_FAILURES` bound as a fresh report, so a failure re-reported inside the window is not handed to the agent twice - including the end the bound trims, because the restore REPLACES that list: keeping its own never-delivered entries over the newer ones would delete failures nothing else holds, recorded in the window and never delivered either. At the bound the restore's own overflow is dropped and reported through the incomplete-restore log. A successful restore must re-emit `feedback`: a second poll can take `waiting` between the destructive take and the restore, and without that wake it long-polls forever over feedback already sitting in `state.json`. And a restore is exempt from the request-wide `MAX_REQUEST_ATTACHMENT_REFS` bound (never from the per-prompt cap or the resolver), because that bound sizes ONE untrusted POST while a delivery accumulates across an unbounded number of them - measuring a restore against it rejects the whole batch and causes exactly the loss restore exists to prevent.
8. The `/events/:key` live-event WebSocket emits server-derived `agent-presence` data. Its state is `waiting` before any poll has attached, `listening` while one is active, and `working` after a poll has delivered feedback and released. Its mode distinguishes `agent-listener`, an owner-labelled `external-listener`, `agent-busy`, and `waiting-on-captain`; the chrome uses external mode to avoid presenting a supervisor-owned listener as an idle captain turn. While the session is open, the chrome keeps feedback actions available because the server queues them for the next poll. An agent reply concludes the working state and returns presence to `waiting`, and a batch delivered with `session_ended` releases it immediately because no later poll or reply can.
   A 200 from `/api/:key/prompts` acknowledges the queue write, not a completed round, so the chrome never promotes itself to `working` on send and renders only the state the stream reports. A successful ownership claim retires the previous round's delivery marker; releasing a poll never does. Presence reconciliation compares state plus mode so a takeover between bare and owner-labelled listeners is visible even when both states remain `listening`.
   Per-note delivery receipts ([docs/delivery-acks.md](delivery-acks.md)) are the same facts stamped on the user's chat entry: `takeFeedback` writes `delivered_at`/`delivered_seq` (Seen), the artifact `reload` event after a delivery writes `working_at` through `markWorking` (Working), and `addAgentReply` writes `done_at` (Done), each only where the previous stamp exists and the next does not. Seen is stamped **by position under the store lock**, not by id: `agentFacingPrompt` strips `prompt_id` from stored prompts at queue time, and because a take drains every pending prompt while `queuePrompts` shares the lock, the user entries with no stamp are exactly the batch being delivered. `session.delivery_seq` numbers takes so a closed-poll restore (`restoreClosedFeedback` passes `delivery_seq` back) removes **only that take's** stamps - deleted, never nulled, because the restore tests assert the entry is byte-identical to its pre-take shape - while a note queued in the window stays unstamped and is delivered by the next take. A refused restore (an attachment no longer resolves) re-queues nothing and still removes that take's stamps and publishes `chat-sync`: a note that reached no agent must not read Seen. Working and Done never cross a reopen: `#upsertSessionLocked` records the last take of an ended session as `closed_delivery_seq`, and `stampWorking`/`stampDone` skip entries delivered at or before it, so a note `textcast-chat-axi end` left at Seen is not marked by a later round's edit or reply. Every stamp change bumps `chat_revision`, which is what makes `syncChat` accept the replacement; `chat-sync` for a delivery is emitted from `finishFeedbackDelivery` (the success path) and again after a restore, never from the destructive take, so no tab is told Seen for a batch about to be put back. `delivery_seq` is stripped from the poll response by `agentFacingFeedback`; agents never see it. A session with no `delivery_seq` key at all predates receipts: `readState` marks its user entries `receipt: "none"` and persists that before any take runs, because the positional rule would otherwise read every one of them as the first post-upgrade batch; marked entries are skipped by every stamp helper and render no receipt row. The chrome derives the receipt row from the entry on every render, and a presence change rewrites only the pre-Seen `receipt-note` line (`refreshUnseenReceipts`), never the bubble, so an "Image expired" placeholder is not rebuilt into a retried image.
   An `ended` live event makes every connected chrome stop accepting feedback immediately; the page and the conversation stay readable and the composer gives way to the reconnect card (`reconnectPrompt`). The channel registers before reading session state, then sends an `ended` snapshot when that state is already terminal; the bootstrapped `initialEnded` state covers pages loaded after the end, and `markSessionEnded()` is idempotent across redundant signals.
   Every poll exit path has to undo the presence it set: `/api/poll` subscribes to request and response closure before its first `await`, re-checks closure and replacement after destructive feedback takes, and reconciles a browser disconnect that occurred before event handlers were armed. This prevents abandoned or displaced polls from stranding ownership, presence, or consumed feedback.
   `--agent-reply` and `--agent-reply-file` publish a chat message through the same atomic poll claim before waiting, rendered in the browser conversation panel via the live stream; README's CLI reference owns when to use each input. `textcast-chat-axi reply` posts that same message to `POST /api/:key/agent-reply` and exits 0 only after the route answers `sent`. The whole receipt request (connect, headers, body) shares one deadline, `AGENT_REPLY_RECEIPT_TIMEOUT_MS`, and a timeout exits non-zero. It must not claim a poll: a poll stays open until feedback arrives, so it cannot be the acceptance receipt.

### Artifact loads

Every artifact load has an **artifact revision**: `session.artifact_revision`, incremented by the server-owned `beginArtifactLoad` epoch before navigation. The artifact document route only verifies the current load and serves it.
The reviewer handoff is a server-issued single-reviewer capability. Begin requests return typed `superseded`, `no-handoff`, or `out-of-order` outcomes; the chrome may re-handshake once for `no-handoff`, but only an explicit takeover reload can replace a superseded reviewer.
The active load is **durable**, not process state: `beginArtifactLoad` writes the whole epoch - token, revision, and the `request_id`/`request_sequence`/`handoff_token` a later begin is judged against - to `session.artifact_load`, and `SessionStore` restores it (and the handoff that owns it) the first time a process asks for it, because the `upgrade` restart replaces the server under reviewers who did not ask for it. Only a newer `beginArtifactLoad` retires a load - not a restart, and not reopening the session. A stored load the restore cannot read as a whole is treated as none, which degrades to one re-handshake and a fresh epoch. The restart tests in `test/session-store.test.js` and `test/server.test.js` pin all three.

### Live reload

`chokidar` watches the artifact file itself by default - watching the entire parent directory recursively saturated the event loop when artifacts lived inside large trees like `~`.
The opt-in attribute/meta (user-facing contract: README's Live reload bullet) switches the watcher to the artifact's directory, excluding `.git`, `node_modules`, `dist`, `build`, `.textcast-chat-axi`.
Any file change emits a `reload` live event and the chrome reloads the iframe; the SDK reports scroll position with `textcast:scroll` and the chrome replays it with `textcast:restoreScroll` after the iframe loads, because the sandbox prevents direct scroll reads.
The same channel preserves the rest of the in-iframe review context: `textcast:reviewState` carries an open annotation card's unsent text and the values of controls inside a `data-textcast-question` scope, and `textcast:restoreReviewState` replays them after the load. Restoration sets values directly and dispatches **no** synthetic `change`/`input` events, because the artifact's own handlers queue prompts and replaying them would silently re-queue answers. Application-owned form state outside `data-textcast-question` is deliberately left alone.
That reported state is also **persisted** per session (`textcast-chat-axi:review-state:<key>` in `sessionStorage`, beside the queue's own key) and restored on boot, because it is the user's own writing and the chrome's in-memory copy dies with the document: an iframe live-reload replayed it, but a full page reload destroyed it, and a real user lost written notes that way. The SDK reports `card: null` when a card is queued or cancelled, which is what retires the stored draft, so a stale draft can never reappear over a later card. `closeCard` reports only when a card was actually open: a page declaring `data-textcast-annotate="off"` closes at boot, and a `card: null` sent then would overwrite the stored draft before the frame's `load` event replays it (`test/artifact-sdk-bundle.test.js`, "reports no review state at boot").
During version-driven shutdown, the server sends `chrome-reload` to the live-event clients of the ONE session named by `POST /shutdown`'s `reload_key` - the session `textcast-chat-axi <file>` is about to open - and `chrome-outdated` to every other connected chrome; a shutdown that names no key (`textcast-chat-axi stop`, idle self-shutdown) reloads nothing. `chrome-outdated` shows a dismissible banner in the conversation panel and never reloads by itself: a forced reload of a current page the user is reading or writing in is the behavior this replaced. The deliberate migration exception is an old EventSource client reconnecting to the retained legacy route: it receives one neutral `chrome-reload` event and the response ends immediately so the tab moves to WebSocket without occupying the browser's HTTP connection pool. `reloadChromeAfterServerRestart` still shows the banner instead of reloading whenever an unsent annotation draft exists. The same banner also carries the server-unreachable state: after `LIVE_EVENT_UNREACHABLE_FAILURES` consecutive live-socket reconnect failures the chrome raises it with the no-reason copy, because an endless silent retry is indistinguishable from a healthy quiet stream and the user learned nothing until they reloaded into a browser connection error. Only that path may retire a banner it raised - a `chrome-outdated` event means the server really was replaced, which a reconnect does not disprove - and a dismissal sticks until the stream actually recovers.
The banner's line is chosen by the shutdown's own `reason` (`SHUTDOWN_REASONS`: `upgrade` and `local-build` from `ensureServer`, chosen by `serverReplacementReason` from whichever branch of `shouldRestartServer` fired, and `stop` from `textcast-chat-axi stop`), and **every branch must be true where it is shown** - a deliberate stop told the user Textcast Chat had been updated, which was false on both counts. An invalid reason on `/shutdown` is dropped and renders the line that claims neither; the legacy migration deliberately sends the unrecognized `server-restarted` reason because the replacement server cannot know why its predecessor stopped. Idle self-shutdown and `shutdownIfNoLiveSessions` need no branch: both only fire with `liveEventClients.size === 0`. Every recovery control this feature shows probes `/health` before navigating - the banner and both gate cards through `checkServerThenReload`, and the inline boot failsafe (`CHROME_BOOT_FAILSAFE_JS`) through its own copy of the same rule, because it runs where `chrome-client.js` does not exist. Each is raised in a state where nothing may be listening, and each is labelled for the check rather than the navigation. Every one of those probes is bounded by an abort timeout and every caller restores its own control on a path that runs whether the probe answers, fails, or times out - a port that accepts a connection and then says nothing would otherwise leave the user's only recovery button disabled, which is worse than the reload it guards. A new one that calls `location.reload()` directly reintroduces the browser error page this whole path exists to avoid; the `superseded` takeover card is the one exception, because its 409 proves the server answered.
The "Textcast Chat is not running." notice is the one failure state only the user retires, so `showLoadNotice` refuses to overwrite it with a non-sticky failure and `clearLoadNotice` leaves it up after a later successful load. The notice never covers the page, and its **Dismiss** button always closes it.
A draft is retired only on a definite answer, and "definite" is deliberately expensive: the SDK re-queries the anchor after `REVIEW_DRAFT_ANCHOR_SETTLE_MS` before reporting `textcast:reviewDraftUnrestorable` (the load event says the document parsed, not that script-built content has rendered), and the chrome retires the stored draft only when a SECOND artifact revision reports that same selector missing. One miss is recorded, not acted on: the element a user annotates is the one the agent is most likely to be rewriting while they type, and an intermediate save that drops it must not delete their notes. Silence is what left an unrestorable draft to be retried against every later load, but retiring on anything less than two revisions is itself data loss. Opening a card cancels the pending settle re-query outright (`showAnnotationCard` -> `cancelPendingDraftRestore`), and the timer also checks `activeCardContext` when it fires: `showAnnotationCard` closes whatever is on screen before it draws, so restoring there would delete text the user is typing that nothing has carried to the chrome yet, and closing that card reports `card: null`, which retires the stored draft - a restore that fired after it would put text the chrome no longer holds back on screen and back into persistence. Retirement is also not silent - `keepRetiredDraft` writes the text verbatim into the conversation panel and persists it under `textcast-chat-axi:retired-drafts:<key>`, so the user keeps a readable copy of writing Textcast Chat can no longer replay; it overwrites nothing they typed and has no control that could discard it. That list is never trimmed to make room: an entry already handed back may not be dropped for a newer one, and a write browser storage refuses is reported in the note itself rather than resolved by evicting an older one.
`reloadChromeAfterServerRestart` must gate the reload on a healthy `/health` answer, never on a deadline alone: reloading into a port nothing is listening on replaces a recoverable page with the browser's own connection-error page, which no Textcast Chat code can undo. A wait that ends on the deadline rather than a confirmed probe re-probes before deciding, because either stale answer is wrong in its own direction.
The "Textcast Chat is not running." notice is **sticky** (`showLoadNotice(..., { sticky: true })`): a later successful artifact load clears an ordinary load-failure notice but must never clear this one, because the page is still running the pre-upgrade client against the replacement server and nothing else would tell the user that. Only the user's **Dismiss** retires it.
Hand-edited files in `dist/` won't trigger reloads.
Run `textcast-chat-axi server --verbose` (or set `TEXTCAST_CHAT_AXI_DEBUG=1`) to log session and watcher events to stderr when diagnosing wedges; detached server stdout/stderr is also appended to `server.log` in `TEXTCAST_CHAT_AXI_STATE_DIR` for startup and crash diagnostics.

### Image attachments

Annotation image attachments (`src/attachment-store.js`) are content-addressed: the id is `<sha256-of-bytes>.<ext>` and the file under `<state-dir>/attachments/<sessionKey>/` _is_ the identity, so the client never dictates a path or id.
The sandboxed artifact iframe can't reach the loopback server (opaque origin), so the SDK annotation card captures the image, reads its bytes, and hands them to the chrome, which performs the same-origin `POST /api/:key/attachments` (raw body, magic-byte validated - a lying Content-Type is ignored) and reports the server-vetted id back to the card. Upload/delete are same-origin guarded like `/api/:key/prompts`.
Two surfaces originate uploads: that relayed card path and the chrome's own Conversation composer, whose controller (`createChatAttachmentsController` in `src/chrome-client.js`) owns its chips, send gate, and notice. They deliberately share the page-wide abuse budget below rather than getting per-surface counters. Three invariants keep the composer honest: its notice is DERIVED from item state on every render (`syncNotice`), because an imperatively stamped "waiting for an upload" string outlived the upload it described once that upload failed; paste/drop resolve their payload through the single `transferredFiles` helper, because several browsers expose a pasted screenshot only through `clipboardData.items` and reading `.files` alone attaches nothing with no error and no chip; and the accepted image types come from `ACCEPTED_IMAGE_MIME` (`src/attachment-store.js`, beside the enforcing `detectImageType`), threaded to the chrome through the session JSON and to the card through `createSdkJs`'s `acceptedImageMime` (`acceptedImageTypes`), so both pickers' `accept` attributes, both paste/drop filters, and the composer's rejection copy are derived - a second hardcoded list would let one surface offer a format the others refuse. Like the annotation card, an over-cap file is decided `error` with no retained `file` and no object URL, so it renders no Retry and its bytes are never read.
Four more composer rules are easy to regress: the chip send gate holds back only the composer's own message and an explicit end - queued annotation prompts still deliver (gating the whole `sendQueued` pipeline made Send silently deliver nothing); paste raises no unsupported chips because Office/macOS pastes expose stray non-image file flavors beside their text (the picker and drop still refuse visibly, and a `Files` drag with nothing enumerable gets an explicit refused chip); the cap counts only uploadable chips (mirroring `currentImageCount`) so a size-refused companion cannot eat a valid image's slot and have `syncNotice` clear the cap notice on the same tick; and a document-level `Files`-drag guard keeps a drop that misses the composer from navigating the chrome away, while leaving text drags to the browser. `planClipboardPaste` (shared rule, duplicated as `keepsClipboardText` in the import-less chrome) treats a pasted file's own name or path in `text/plain` as placeholder, not caption.
The upload route reads the request stream itself via `readAttachmentUploadBody` rather than `express.raw({ limit })`: raw-body aborts on a too-large `Content-Length` WITHOUT draining, which leaves the browser's in-flight upload reset mid-stream so the chip hangs on "uploading" instead of getting the 413. The manual reader buffers up to the cap but always drains to end-of-body, then the route sends a clean 413. Belt-and-suspenders, the chrome also pre-checks byte length against `attachmentMaxBytes` (surfaced in the chrome session JSON) and fails the chip locally before uploading. Do not reintroduce a body-parser `limit` on this route.
Because the sandboxed frame's postMessage source proves origin but not a user gesture, the chrome is the **confused-deputy mediation point** for the relayed card path, and its counters are page-wide, so the composer's own user-gesture uploads spend the same budget: it rate-limits (`UPLOAD_RATE_MAX`/`UPLOAD_RATE_WINDOW_MS`), enforces a per-chrome-session cumulative-byte quota (`UPLOAD_SESSION_BYTE_QUOTA`), AND bounds concurrent in-flight uploads (`UPLOAD_MAX_IN_FLIGHT`, D8 - rate + cumulative alone let ~30 large bodies fetch at once before the quota tripped) before any upload reaches the loopback server; over-cap uploads are refused with a retry hint and a settled upload frees a slot. The server keeps a bounded default disk quota (`DEFAULT_MAX_ATTACHMENT_DISK_BYTES`) as the durable backstop.
The **trust boundary** is `SessionStore.queuePrompts`: a queued prompt carries only the client's `id` + display `name`; `resolvePromptAttachments` re-derives every authoritative field (absolute `path`, mime, bytes, dimensions) from disk via the injected resolver, so a crafted `/prompts` POST cannot aim an attachment at an arbitrary file. Repeated content ids remain repeated logical references with their own display names and count separately toward prompt count/byte caps; content-addressed storage deduplicates only the bytes on disk. Resolution is **all-or-nothing** (C4): a malformed field/entry, any unknown id, or a count/byte-cap breach rejects the whole batch (`{ rejected, caps }`, persist nothing → 400), never a silent partial-drop; the chrome keeps its queue on the 400 and surfaces the reason. User-facing limits/env vars and defaults are owned by README's Image attachments bullet.
`boundAttachmentRefs` runs BEFORE the resolver and is why a crafted batch can't wedge the server: the in-resolver cap counts RESOLVED refs, and a well-formed id for a file that doesn't exist never advances it, so thousands of them would each buy a sequential `stat` while the store's single mutex is held, stalling every poll and mutation. Raw per-prompt and request-wide (`MAX_REQUEST_ATTACHMENT_REFS`) counts are rejected up front - except that a closed-poll restore is exempt from the request-wide bound alone, for the reason given in Request flow step 7 - and the reported rejection list is capped (`MAX_REPORTED_ATTACHMENT_REJECTIONS`) so the 400 can't be turned into an amplifier. New pre-resolve validation belongs in that same pure gate - never after the first `await` into the filesystem.
`SessionStore` owns ONE `AsyncMutex` (`src/async-mutex.js`, `store.lock`) covering BOTH concerns. Every `state.json` read-modify-write runs under it - `queuePrompts`, `takeFeedback`, `recordArtifactFailures`, `upsertSession`, `endSession`, `addAgentReply` - so a poll can't clear prompts in the window `queuePrompts` holds its pre-resolve snapshot and then clobber the take (E1); **any new store mutation must acquire this lock too**. The server routes its attachment disk sections (upload finalize, delete, the sweep) through `store.runExclusive` so they share that same lock, keeping the reference snapshot + delete atomic against `queuePrompts` (D5). `referencedAttachmentIds` is a pure read and must stay lock-free - the server calls it from inside `runExclusive`, so self-locking would deadlock. Delete is **reference-counted** under the lock - a content-addressed file shared by a queued prompt survives a DELETE request (`status: "referenced"`) - and dedup re-upload **refreshes the mtime** so a re-referenced aged file isn't reaped by the next sweep (B3).
Dimensions are persisted at upload in a `<id>.meta` sidecar (D6): `resolveAttachment` reads it instead of re-parsing the whole image, and the thumbnail GET uses `statAttachmentForServe` (one stat + streamed send, mime from the id extension) instead of a second full read. Sidecars are removed with their image on delete/sweep and are excluded from `listAttachments` by `ID_RE`.
The SDK's annotation card gates queuing on BOTH `hasPending()` (R2.4, an in-flight upload) AND `hasErrors()` (W2, a failed/rejected chip) so neither is silently dropped by `collectReady`/`closeCard` - it keeps the card open with a notice so the user can wait, retry, or explicitly remove; that notice line is shared with the card's neutral keyboard hint, so it renders in the error color and is restored (never left stale) once the condition clears. A count-cap rejection remains visible while the card is full and clears only when removing a chip creates capacity. A mixed drop **partial-accepts**: `partitionDroppedFiles` always reports both halves, so the images attach AND every unsupported companion raises its own `UNSUPPORTED_TYPE` chip - reporting the unsupported files only when no image was found is what made a mixed drop swallow them silently. Removing a chip deletes **nothing**: there is deliberately no `textcast:removeAttachment` message and the chrome honors no iframe-driven delete, because the iframe is untrusted and no client can see every live reference (attachments are content-addressed, so another tab's ready-but-unqueued chip shares the id and is invisible from here). Only the reference-aware sweeper and the reference-counted same-origin `DELETE` route remove unreferenced attachments; the chrome never drives the latter, so do not reintroduce an eager delete. Upload results are scoped to the document that asked for them: each document mints an `ATTACHMENT_NONCE`, sends it with every upload, and `isTrustedAttachmentResult` requires both an exact nonce match and `event.source === parent` - chip ids restart at `att-1` on every load, so id alone would let a result in flight across a reload mark a new chip with the previous document's image. The card's per-prompt count cap is NOT a literal: `createSdkJs` threads the server's `maxPerPrompt` into the SDK so the local guard matches `TEXTCAST_CHAT_AXI_MAX_ATTACHMENTS_PER_PROMPT` (W1), and an over-cap pick is surfaced instantly rather than swallowed. Queued and sent note bubbles always render at most four thumbnails and collapse every additional attachment into an explicit `+N` badge, independent of that configurable cap (`test/chrome-client-queue.test.js`). The card re-clamps its viewport position after every attachment-row render (W3) so chip rows can't push Queue/Cancel off-frame; the chip list also has a `max-height`/scroll backstop.
Cleanup (`sweepAttachments`, run at server startup + hourly) is **reference-aware** and never removes a file in `SessionStore.referencedAttachmentIds()`. It has two distinct passes: TTL cleanup reaps an unreferenced file once it is past its TTL (`TEXTCAST_CHAT_AXI_ATTACHMENT_TTL_MS`, seven days by default), and cap eviction, under disk-cap or object-cap pressure, removes unreferenced files oldest first before their TTL, but only once they are older than `ATTACHMENT_EVICTION_GRACE_MS` (one hour) - so a send-and-end batch's images are never lost before delivery, and orphaned uploads (card cancelled, or `/prompts` never followed) are reaped later.
That reference set is pending-prompt ids **plus** ids delivered within `ATTACHMENT_DELIVERY_GRACE_MS`: `takeFeedback` clears the delivered prompts, so without that window an attachment would become sweepable at the exact moment the agent starts reading the path it was just handed. The grace is a bounded read window, not a second lifetime (the TTL and disk cap must still reclaim delivered bytes eventually), and the retained list is capped (`MAX_DELIVERED_ATTACHMENTS`) because it lives in `state.json`, which is rewritten wholesale on every store operation.
The eviction grace is the symmetric window on the upload side (fixed, not env-tunable): "unreferenced" also describes a **ready chip** - an image sitting in an open annotation card or the Conversation composer that has not queued a prompt yet - so cap eviction with no age floor deletes bytes out from under the imminent Send, which then fails unrecoverably as not-found. It never lets the total exceed the cap, because admission refuses the new write instead.
The disk cap charges **allocated** cost, not logical image bytes: `listAttachments` reports `chargedBytes` = the image rounded up to whole `ATTACHMENT_ALLOC_BLOCK_BYTES` (4096) blocks plus the sidecar's own block, and both of its enforcement points measure `maxDiskBytes` against that accounting. Summing logical `size` let a flood of 12-byte magic-prefix uploads (the smallest `detectImageType` accepts) sit ~683x under the reported total while consuming real disk and inodes.
The periodic sweep is only one of those two points, and it can never hold the cap alone: it refuses to evict referenced or in-grace files, so concurrent chrome pages could each write past `maxDiskBytes` in the window before the next sweep. `admitAttachmentCharge` inside `writeAttachment` is therefore the single **upload-admission chokepoint** every byte-adding write path must route its charge through (today a new image+sidecar and the dedup sidecar repair; the dedup mtime rewrite replaces identical bytes and the sweep only removes): it reclaims toward `cap - newCharge`, measures the true committed allocation with its own tree walk so the undeletable temp/orphan debris a curated survivor set hides is still counted, and refuses with **507** when the write would not fit. Admission must run under the store's lifecycle lock so the reference snapshot, the reclaim, and the write are one critical section; a refused sidecar repair is skipped (the sidecar is only a display cache) rather than failing the dedup upload. The `maxObjects` bound is **derived** from the disk budget (`budget / 2 blocks`), never a separate env var, so it can only agree with the byte cap. The sweep's cap/object eviction keeps **running totals** decremented per removal rather than recomputing over all survivors per candidate: it runs under the store's global mutex, so per-candidate O(n) work would be an E3-class lock hazard. The sweep also reaps files that `ID_RE` hides from every cap: crash-orphaned temp files (D6) - `writeFileAtomically` writes `<name>.<pid>.<n>.tmp` then renames, and a crash in between leaves one, reaped once older than a 5-minute grace (a live write renames within ms) - and orphan `<id>.meta` sidecars whose image is gone (ATTACH-002), reaped with no grace since a live upload writes the image before its sidecar. `removeAttachment`/`removeFile` delete the sidecar FIRST, so a crash between the two removals leaves only the counted image, never an uncounted orphan sidecar. The SDK decides a whole drop in one pass via the pure `classifyAttachmentBatch` (mime / size / count-cap per file) and `addFiles` renders **once** instead of per file (D7 - a large multi-drop was O(N²) DOM rebuilds); `rejectUnsupportedBatch` does the same for unsupported files. The size decision lives in that classifier and still runs **before** `createObjectURL`/`arrayBuffer` (`attachmentSizeError`, threaded from the server via `createSdkJs`'s `maxAttachmentBytes`), so an oversized drop is decided `error` and never read into a buffer or structured-cloned into the chrome; the server still re-checks.
Attachment files and dirs are created **owner-only** (`0600`/`0700`, set explicitly at creation since the umask would otherwise leave 0644 in traversable dirs) and `ensureAttachmentDir` re-asserts the dir modes so an install that uploaded before that hardening doesn't keep its existing screenshots exposed. A dedup upload's mtime refresh is load-bearing (it restarts the TTL clock) and must never be swallowed into a success: `writeAttachment` falls back to an atomic rewrite of the identical bytes and propagates if that fails too. Env limits floor BEFORE the bounds check and require `>= 1`, so a fractional `0.5` falls back instead of flooring to a silent zero cap; only `0`/`off` may disable one.

## Things to know when editing

- `run()` short-circuits `--version`/`-v`/`-V` (`isVersionOnlyArgv`) before `ensureStateDir`, because agent harnesses probe every tool's version at session start. Any new startup work must go after that short-circuit; `test/cli-version.test.js` guards the "no state dir" property.
- `canonicalFile` runs `realpath`, so symlinks resolve to their target before becoming session keys. Two paths that refer to the same file always collapse to one session.
- The SDK injected into artifacts lives in `src/artifact-sdk.js` and is wrapped by `createSdkJs`.
  It executes inside an iframe sandboxed with `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox allow-downloads` (no `allow-same-origin`), so it cannot read the chrome's DOM - communication is `postMessage` only. `allow-popups-to-escape-sandbox` lets popups render as top-level tabs without weakening the artifact iframe. Every `/artifact/*` response also carries the matching CSP `sandbox` policy, so an escaped popup that navigates to an artifact-owned active document remains opaque-origin and cannot become a same-origin application client.
  EVERY artifact→chrome message must go through `postArtifactMessage`, the only send path that stamps the current `artifact_load_token`: the chrome's message listener drops any frame message whose token is not the current load's before dispatch, so a raw `parent.postMessage` is silently discarded (a token-less `textcast:uploadAttachment` shipped exactly this break while every mocked harness stayed green - the chrome harness must therefore send test messages verbatim, never patch the token in).
- Any helper `createArtifactSdk` calls must reach the browser through `serializeModuleHelpers` in `createSdkJs`, which turns every export of a shared module (`src/artifact-revisions.js`) into a same-scope `const`. A module-private function called from the SDK closure compiles fine and only `ReferenceError`s on the first click, so put new helpers in a wholesale-serialized module and export them; a helper may then reference only its own arguments, browser globals, or its sibling exports - never a module-level constant, which is not serialized. Those modules must export functions and nothing else: only functions survive `toString()`, so `serializeModuleHelpers` throws on any other export rather than shipping a `Set` or `RegExp` that would arrive as an empty `{}`. `test/artifact-sdk-bundle.test.js` boots the served bundle and drives a real click, which is what catches an unreachable helper; the module-level unit tests cannot.
- Annotation handlers ignore native controls (`button`, `input`, `select`, `textarea`, `option`, `label`, `summary`, editable regions, and elements with an interactive ARIA widget role such as `role="button"` or `role="menuitem"`) and their descendants, so they stay interactive without markup; an `<a href>` stays annotatable when it carries such a role or sits inside such a widget, because a passed-through click would navigate the artifact frame away; `data-textcast-action` opts custom non-native controls out of annotation and gives them a pointer cursor. The user-facing contract for input patterns (`data-textcast-question`, `queueKey`) is README's Feedback controls bullet.
- For text annotations, `prompt.selector` is the common ancestor/container selector, not the complete identity. Use the `target` range boundaries to locate the exact selected text.
- `SessionStore` re-reads and re-writes the entire `state.json` on every operation - there is no in-memory cache. The single server process is necessary but NOT sufficient for consistency: a method that reads state, `await`s, then writes can still interleave with another method's read-modify-write and lose its update. Every mutation therefore serializes through the store's single `AsyncMutex` (`store.lock`); see the Image attachments section (E1) for the full invariant and the one lock-free exception (`referencedAttachmentIds`).
- Below 860px the conversation panel is a fixed bottom sheet with a persistent dock (the phone block in `src/chrome.css`; README's Reviewing on a phone bullet owns the user-facing behavior), and the chrome's sheet controller in `src/chrome-client.js` owns open/closed intent, `inert` on the hidden half, focus handoff, gestures, visual-viewport synchronization, and the dock summary. `MOBILE_SHEET_MEDIA` there must match the CSS breakpoint. Four rules are easy to break: desktop stays pixel-identical only because `.panel-head`/`.panel-head-row` are `display: contents` outside the breakpoint (the `h2` must remain a direct flex child of `.panel`); the collapsed state is a `translateY`, never a height change, so the chat keeps its layout and the sheet can follow a drag, which is also why the phone panel carries a shadow hairline instead of a border (a 1px border pushes the docked head past the viewport edge); the sheet is sized from `--vv-top`/`--vv-height`, which `syncVisualViewport` keeps equal to the visual viewport, so the iOS keyboard shrinks it instead of covering the composer (Android gets the same through `interactive-widget=resizes-content` in the viewport meta, and `viewport-fit=cover` is what makes the `env(safe-area-inset-*)` padding non-zero); and the mobile composer is its own scrollport with sticky send actions while `.panel-scroll` yields its minimum height first under visual-viewport pressure, keeping the actions reachable even with attachments and a keyboard. Real geometry is pinned by the opt-in `test/mobile-conversation-sheet.browser.test.js`. The desktop panel collapse (`#sidebarToggle`, `body.panel-collapsed`, one viewer-wide `localStorage` key) must never reach the phone layout: its CSS sits under `@media not all and (max-width: 860px)`, the exact complement of the sheet breakpoint, and the client sets the class only while `MOBILE_SHEET_MEDIA` does not match, so a stored collapse cannot hide the dock.
- The chrome and the sandboxed artifact document cannot see each other's keyboard events (no `allow-same-origin`), so any keyboard shortcut that must work regardless of focus needs its own capture-phase `document.addEventListener("keydown", ..., true)` in _both_ `src/chrome-client.js` and `src/artifact-sdk.js`, not just one.
  The annotate/explore mode toggle hotkey (`MODE_TOGGLE_HOTKEY_KEY`, Cmd/Ctrl+I) is the reference implementation: the SDK initializes from `data-textcast-annotate` on the root html element (only `"off"` disables), and reports that default once with token-stamped `textcast:annotationMode`. The chrome accepts one boolean default per artifact load until the reviewer explicitly toggles, then keeps that choice across artifact reloads and reconciles it back to the SDK, including when frame-load replay arrives before the default report. On catching the hotkey the SDK sends `{ type: "textcast:toggleAnnotationMode" }` to the chrome, which drives the exact same `toggleAnnotationMode()` function the on-screen switch's `onclick` calls.
  Requiring a modifier (`metaKey || ctrlKey`) is what lets the listener safely call `preventDefault()` without breaking plain typing (including typing the bound letter itself) in the chat box or an annotation-card textarea.
- Tests use `TEXTCAST_CHAT_AXI_STATE_DIR` and ephemeral ports to stay isolated. When adding tests that spin up the server, do the same.
- Circular close buttons (`.queued-remove`) render an inline SVG x mark with two symmetric strokes, not a text `x`/`&times;` glyph.
  Font metrics put text glyphs off from the geometric center even under flex centering, while the SVG centers via flex plus equal viewBox margins.
  Keep the SVG strokes on `currentColor` so existing hover color rules still apply, and follow this pattern for any new circular icon-only button.
- Only `chrome-client.js` points the artifact frame at the page, so a page whose client never runs stays empty. `CHROME_BOOT_FAILSAFE_JS` is inlined BEFORE the `<script src="/chrome-client.js">` tag (a request that hangs rather than errors blocks parsing, so a failsafe placed after the tag would never be reached) and shows the load notice on the script's `onerror` or boot timeout. The client cancels that timer by setting `window.__textcastChromeReady` at the very end of the file. Keep the placement, timeout, end-of-file cancellation, ended-session guard, and the bounded `/health` probe behind **Check and reload**.
- The artifact iframe carries only `data-artifact-src` and is navigated exclusively by `replaceArtifactFrame`, so a chrome whose FIRST begin-load fails has no previous frame to preserve - abandoning the load there leaves an empty frame and an `artifact_revision` that never advances, which is what a session reopened across a server restart looked like. Recoverable outcomes (a transport failure past `ARTIFACT_LOAD_BEGIN_RETRY_DELAYS_MS`, or a `no-handoff` whose one re-handshake also failed) must schedule a fresh attempt through `ARTIFACT_LOAD_RECOVERY_DELAYS_MS` and, once that is exhausted with nothing on screen, surface `showLoadNotice` instead of a silent blank. `superseded` and `out-of-order` must NOT retry: another reviewer or a newer request in this same chrome owns the artifact, and a background retry would fight it. A `superseded` chrome that has nothing on screen still has to say so on the load notice (`showLoadNotice` with a takeover reload), because the takeover banner lives in the conversation panel, which may be minimized - without that the reader sees an empty page with its only recovery control out of sight. A `superseded` chrome that already shows an artifact must keep it and use the banner alone.
- The revision legend (`src/artifact-revisions.js`, README's Revisions legend bullet) reads an agent-declared `data-textcast-revisions` registry and `data-textcast-revision` marks; the SDK is read-only and never marks up the artifact, so the served bytes stay identical to the file on disk. Three invariants are easy to break by accident:
  - `resetRevisionLegend()` in `src/chrome-client.js` must run only right before `replaceArtifactFrame` actually reassigns `frame.src`, never unconditionally at the top of that function. A preserved load (`superseded`, `out-of-order`, an exhausted retry) never reassigns `frame.src`, so clearing the legend there strips it from an artifact that is still on screen and whose SDK will never re-report it.
  - The legend's per-row cap (`entries` in both `revisionLimits()` and the chrome's `REVISION_LIMITS`) must derive from the shared `revisionPalette()` length, not a second hardcoded number - a cap that outgrows the palette hands two revisions the same colour, border, and pattern.
  - The chrome re-validates the postMessage payload as untrusted input from a sandboxed frame: an id or selector over its length limit is rejected outright, never truncated, because a truncated id can collide with another revision's and a truncated selector is still valid CSS pointing somewhere else. `__proto__` is a legal revision id, so lookups use a `Map`/`Set`, never a plain object key.
